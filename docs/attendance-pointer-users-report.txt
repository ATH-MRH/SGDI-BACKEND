EXTENSION — SOUS-UTILISATEURS POINTEURS DEPUIS POINTAGE

SOUS-UTILISATEURS POINTEUR : OUI.
UTILISATEURS CENTRAUX : OUI, table users et user_id central.
NOUVELLE TABLE UTILISATEURS : NON.
MIGRATION NOUVELLE POUR CETTE EXTENSION : NON.
Le modèle central possède déjà les comptes, le statut, les modules, les actions,
les périmètres, les tables de permissions et l'audit nécessaires.

AUDIT AVANT EXTENSION
User contient username unique, email facultatif unique, full_name, role,
access_level, authorized_modules/actions/societies/sites, global_society_access,
is_active et les mots de passe hachés. Aucun champ last_login ni created_by
n'est nécessaire : ces informations sont conservées par le journal central.
L'Administration utilise le rôle métier pointeur et le profil existant H2.
Le formulaire central normalisait auparavant les rôles terrain inconnus vers
agent ; pointeur est maintenant conservé explicitement dans ce formulaire.
Le service central normalize_username continue à normaliser les identifiants.
La convention PTG01 est reprise dans le formulaire ; aucune seconde logique de
génération ni inventaire global des identifiants n'est exposé au responsable.
Email : facultatif dans User ; aucune adresse ni mot de passe de validation
supplémentaire imposés à un compte qui ne possède aucun droit de validation.
Aucun email de création n'est envoyé par cette interface.

RÔLE POINTEUR RÉUTILISÉ : pointeur.
PROFIL : H2, saisie terrain.
MODULES : authorized_modules = [pointeur], application pointeur.irongs.com.
ACTIONS : authorized_actions = [read, create].
Permissions canoniques : attendance/read et attendance/create ;
attendance/qr_scanning/read, create et attendance/manual_entry/read, create.
Aucun admin, delete, unlock, export, validate, ni module DRH/OPS/Finance/
Commercial/Matériel/Administration accordé au Pointeur créé.
La borne faciale conserve son identité d'appareil et n'acquiert pas de compte humain.

PERMISSIONS DU RESPONSABLE
Source : UserFeaturePermission, module canonique administration,
fonctionnalité users, actions read/create/update, ou admin déjà existant.
Les administrateurs explicitement globaux gardent leur politique centrale.
Les actions individuelles du responsable limitent aussi les capacités affichées.
L'entrée Administration → Pointeurs est masquée sans read ; ajout et modification
sont affichés seulement avec leurs actions respectives. Le serveur vérifie tout.
Ces permissions déléguées n'ouvrent pas l'API globale /auth/users à un compte terrain.
Elles restent attribuées par les mécanismes de RBAC de l'Administration système.

API AJOUTÉE (préfixe /api/attendance/pointers)
GET /capabilities : droits effectifs et sociétés/sites attribuables.
GET : liste autorisée et KPI calculés (total, actifs, désactivés, sites couverts).
POST : création par le service central create_user, puis permissions et audit
atomiques dans la même transaction.
PATCH /{user_id} : nom, statut, sociétés et sites, sans champ de permission avancée.
Aucune route DELETE ni hard delete dans l'interface Pointage.
Les schémas refusent les champs supplémentaires (rôle, module, action, accès global...).

SOCIÉTÉ EXPLICITE OBLIGATOIRE : OUI.
SITE EXPLICITE OBLIGATOIRE : OUI, un ou plusieurs.
Périmètre attribuable = intersection des sociétés centrales et sites autorisés
au responsable. Chaque site doit appartenir à une société choisie.
Un Pointeur dont le périmètre complet dépasse celui du responsable est invisible
et n'est pas modifiable ni réactivable par lui. Aucun filtrage partiel ne remplace
silencieusement les autorisations centrales d'un compte.
Les gardes centrales de création/modification et d'authentification protègent
également les Pointeurs contre des périmètres vides, globaux ou incohérents.
La réactivation depuis l'Administration repasse par la même validation.

ESCALADE PRIVILÈGES BLOQUÉE : OUI, contrôlée côté serveur.
VISIBLE POINTAGE.IRONGS.COM : OUI, section Administration → Pointeurs.
VISIBLE ADMINISTRATION SYSTÈME : OUI, mêmes utilisateurs centraux.
La fiche centrale préserve le rôle pointeur et précise aussi les périmètres obligatoires.

CRÉATION : OUI, nom, identifiant, mot de passe, sociétés, sites et statut ; email facultatif.
MODIFICATION : OUI, nom, statut, sociétés et sites dans le périmètre du responsable.
DÉSACTIVATION : OUI, confirmation et statut central is_active=false, sans suppression.
Un compte désactivé ne peut ni se connecter ni utiliser son ancien jeton pour pointer.
La vue, la recherche et les KPI sont recalculés après mutation.
Les données de la vue et les modales sont effacées à la déconnexion.

AUDIT
pointer_user.created / updated / disabled / scope_changed.
Auteur responsable (user_id), cible (resource_id=user_id du Pointeur), date,
périmètre précédent/nouveau, état et profil ; aucun mot de passe journalisé.

Les comptes anciens sans événement de connexion indiquent « Non enregistrée ».
La relation de gestion est tracée par l'audit, pas par une seconde identité.

POINTAGE ET TERMINAL
Attendance Core existant conserve déjà actor_user_id, actor_label, site_id,
source, date/heure, résultat et données du pointage. Un scan QR réel dans le test
backend vérifie que le Pointeur central est l'acteur de l'événement.
Les identités de terminal (public_id/clé ECDSA) restent distinctes des comptes humains.
L'extension ne change pas le protocole de terminal ni ne prétend transformer une
session humaine en identité d'appareil. Aucun algorithme d'Attendance Core modifié.
